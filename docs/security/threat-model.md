# RelayBridge Threat Model

- Status: Updated for Milestone 7
- Last reviewed: 2026-08-24

## Scope and trust boundaries

RelayBridge will bridge untrusted or weakly trusted LAN SMTP devices to a
customer's Microsoft 365 tenant. Important trust boundaries are the LAN socket,
local management browser, process/service identity, SQLite metadata, filesystem
spool, Windows certificate/secret stores, Microsoft identity endpoint, and Exchange
SMTP endpoint.

Milestones 1–7 add the LAN SMTP socket, device password verifiers, SQLite metadata,
raw filesystem spool, queue worker, retry, reconciliation, and disk-capacity
boundaries, plus a tenant-specific Microsoft application identity using a Windows
certificate, the Exchange SMTP OAuth delivery boundary, and the loopback Microsoft
setup wizard, and the loopback device-management UI. The listener binds to
loopback by default and a fresh database has no devices. The production provider
is present but workers are disabled by default and will not start with missing or
unusable local identity. The web host exposes local status, queue health, and the
M5 setup route, and the M7 diagnostics route; it does not expand the loopback
management binding. Diagnostics remain local, non-telemetric, and non-administrative.

## Assets

- customer message bodies, attachments, envelope metadata, and operational history
- device password verifiers and management credentials
- OAuth access tokens and authentication-certificate private keys
- sender authorization, device, queue, and retention configuration
- host availability, disk capacity, and delivery integrity

## Threats and controls

| Threat | Impact | Required mitigation | Residual risk |
|---|---|---|---|
| Compromised printer | Unauthorized mail and queue consumption | Implemented per-device identity, IP/subnet and sender restrictions, message/count/byte/free-disk limits, and disable control | A permitted device can consume its capacity allocation; per-device time-window rate limits remain deferred. |
| Hostile LAN device | Brute force, spoofing, denial of service | Loopback default, authentication by default, global/per-source connection bounds, three AUTH attempts per session, line/message limits, idle timeout; cleartext AUTH requires one explicit RFC1918/ULA bind and rejects wildcard/public/listener ambiguity | Source IP is not identity on a compromised LAN; cleartext credentials remain observable on a compromised trusted LAN and time-window login throttling remains deferred. |
| Open relay abuse | Spam, tenant compromise, reputation and cost damage | Fresh install has no devices; every device requires IP and sender allow-lists; Legacy rejects public/catch-all networks; tests cover anonymous, wrong-IP, and wrong-sender paths | An explicitly authorized or compromised device can send to unrestricted recipients in Milestone 1. |
| Stolen SMTP password | Device impersonation | 192-bit generated secrets, salted PBKDF2-HMAC-SHA256 verifiers, one-time provisioning/reset display, source restrictions, no credential logging, cleartext AUTH disabled by default | STARTTLS is absent; explicitly enabling cleartext AUTH exposes the reusable password to LAN interception. |
| Password disclosure through device UX | Reusable device impersonation | Plaintext exists only in the in-memory interactive component immediately after create/reset, requires explicit reveal/copy, and Test, Finish, reset-again, and controllable navigation are blocked until saved-password acknowledgement; secret-bearing domain/result string output is redacted; plaintext is never stored in SQLite, URL, local storage, logs, or printed instructions | Browser refresh or an uncontrolled process exit can still discard plaintext; a local user, extension, screen capture, or clipboard monitor can observe a deliberately revealed/copied password. |
| Misleading printer setup/readiness or privileged apply abuse | Failed setup, accidental unsafe binding, or LocalSystem write/restart primitive | Persisted Microsoft configuration is Verification required after restart; direct verification uses that active configuration through certificate/private-key validation, token acquisition, trusted STARTTLS, and XOAUTH2/QUIT without a mail transaction or tenant mutation. Printer preparation shows only active private candidates and rejects loopback/public/wildcard choices. One-click Apply requires UAC and a dedicated installed NativeAOT helper; a one-shot current revision carries no path/JSON/command, Host verifies actual helper PID/session/path/hash, and the helper authenticates the SCM-owned LocalSystem service. It reconstructs the exact listener/queue schema, verifies the fixed Program Files tree, replaces only `Host\appsettings.Production.json`, restarts only `RelayBridge`, and reports success only after health and listener readiness. Manual firewall guidance remains program/address/port scoped to Private profile; RelayBridge does not modify firewall state. | A local Administrator can already replace installed application configuration and remains outside this boundary. Interface selection still requires administrator judgment; startup-bound listener changes require a service restart, and RelayBridge does not probe printer reachability. |
| Unsafe legacy-device provisioning | Open-relay expansion or source spoofing | Legacy setup requires an explicit private/local IP or constrained subnet plus the active sender; catch-all/public networks fail domain validation and ambiguous overlap fails closed | IP identity remains weak on a compromised LAN and inbound TLS is not yet available. |
| Device-management mutation abuse | Device disablement, credential reset, authorization changes, or lost updates | Management binding is code-owned loopback and rejects non-loopback overrides; validation is repeated in the domain layer; destructive actions require confirmation; duplicate UI events are guarded; schema-v6 compare-and-swap revisions advance on edit/reset/disable/enable; narrow updates and affected-row checks reject stale/concurrent operations | A malicious local user or compromised browser session can administer devices until authenticated management is implemented. |
| Sender spoofing | Mail sent as executives or protected identities | Device sender allow-list and Exchange RBAC mailbox scope; negative authorization tests | Exchange or RelayBridge policy misconfiguration can broaden scope. |
| Malicious MIME | Parser exploits, UI injection, downstream attacks | Raw opaque spool, minimal parsing, patched dependencies, encode displayed metadata, never execute content | Exchange and recipients still process attacker-controlled content. |
| Huge-message attack | Disk or memory exhaustion | DATA is streamed with message/line limits and bounded connections; metadata-backed message-count/spool-byte limits, active-session reservations, and a free-disk floor reject with temporary failure | Capacity is process-wide rather than per-device, so one authorized device can deny intake to others without exceeding global bounds. |
| Connection exhaustion / slow sender | Service denial | Implemented bounded concurrent sessions, per-IP limits, command counts, and per-read idle timeout | No throughput-rate floor yet; legitimate slow devices may need tuned limits. |
| Authentication brute force | Credential discovery, CPU exhaustion, and log flooding | Three attempts per session, per-source connection bounds, serialized PBKDF2 verification, structured security events, and no credential detail leakage | Time-window throttling is deferred; distributed or sustained attempts can occupy the single verification slot. |
| RelayBridge server theft | Offline disclosure and identity theft | Random spool paths, no plaintext password storage, immediate delivered-payload cleanup, and bounded queue storage are implemented; OS account isolation, restrictive installer ACLs, disk encryption guidance, and failed-payload retention remain | A determined attacker with filesystem access can read queued/failed message content and password verifiers. |
| Database theft | Device/config/history disclosure | No plaintext secrets or message bodies in SQLite, ACLs, privacy-minimal metadata | Metadata can remain sensitive. |
| Spool theft | Full message disclosure | Restrictive ACLs, random paths, minimal retention, disk encryption guidance | Service identity and local administrators require access. |
| Certificate theft | Microsoft application impersonation | Implemented non-exportable generated CNG key, Windows `My` store references, actual signing access check, public-only export, expiry state, and no private material in SQLite/logs | Host compromise or a local administrator can use a key while the service identity can access it; production service-key ACL installation is deferred. |
| Certificate misconfiguration or expiry | Authentication outage | Exact thumbprint match, duplicate rejection, validity/algorithm/key-size/signing checks, warning threshold, and plain-language state; configured certificates are never auto-deleted | Renewal and Entra registration remain administrator-controlled; full rotation UI is deferred. |
| Token leakage | Tenant impersonation until token expiry | Safe token wrapper, in-memory MSAL cache only, JSON/string redaction, allow-listed logging and tests; no persistent token or client-secret schema | A debugger or compromised process can read live token memory. |
| Wrong tenant/application or credential replacement | Authentication failure or unintended identity | Non-empty GUID validation, fixed Microsoft authority construction, one identity configuration, cached-client invalidation, safe correlation codes | An administrator can still deliberately configure the wrong customer-owned identity. |
| Microsoft identity compromise | Unauthorized tenant mail | Customer-owned single-tenant app, certificate auth, RBAC-only scoped role, no additive unscoped grant, audit and rotation | Exchange or tenant-admin compromise is outside local control. |
| Local administrator compromise | Complete service, secret, and mail compromise | Document trust boundary, minimize service privilege, audit config changes, avoid unnecessary secret export | Local administrator control cannot be fully defended against. |
| Log leakage | Exposure of tokens, credentials, addresses, subjects, or content | Structured allow-listed fields, redaction tests, never log AUTH payloads/tokens/passwords/body/attachments | Operational metadata can still reveal relationships. |
| Diagnostic bundle leakage | Portable disclosure of sensitive state | Fixed versioned entry allowlist, anonymous export DTOs, 1 MiB cap, hostile-fixture scans, and exclusion of raw configuration/database/log/spool data, addresses, messages, credentials/verifiers, tokens, private keys, certificate references, and detailed setup errors; generation is local and never uploaded | Versions, timestamps, counts, local listener/network metadata, storage capacity, and safe status summaries can still be operationally sensitive and require administrator review before sharing. |
| Diagnostic probe leaks credentials or sends mail | Token disclosure, unauthorized delivery, or misleading acceptance claim | Fixed unauthenticated probe performs only DNS, TCP 587, greeting, EHLO, STARTTLS, and normal certificate-validated TLS under one bounded deadline; it has no token-provider dependency and sends no AUTH, envelope, DATA, or message | A successful probe proves only contemporaneous network/TLS reachability, not Microsoft identity, sender authorization, SMTP acceptance, or inbox delivery. |
| Dependency or update compromise | Code execution or data theft | Few dependencies, lock and review versions, CI restore/build/test, vulnerability monitoring, signed releases later | Build ecosystem and trusted maintainers remain supply-chain dependencies. |
| Installer-time Graph/Entra package substitution or unsafe archive | Administrator code execution during later Microsoft setup | M9.1 uses four immutable package identities and official Gallery HTTPS URLs only. Burn validates fixed size/SHA-512; a networkless NativeAOT provisioner independently validates SHA-256, nuspec ID/version, declared license/dependencies, signature payload, bounded path-safe extraction, protected staging, and the exact schema-v2 file closure before transactional Program Files commit. Changed upstream bytes, malformed acceptance, traversal, reparse, ACL, or closure mismatch fail before service start. | Microsoft/Gallery compromise that can serve the exact pinned bytes is outside the local model. Development artifacts are unsigned and public Windows binary release remains prohibited pending signing. |
| Repeated Host crash | Extended outage or unbounded restart loop | The installed own-process service restarts after the first and second crash with a 15-second delay, resets the failure window after one day, and performs no third automatic restart. Durable queue recovery remains authoritative after restart. | Persistent faults require administrator diagnosis; a message at an uncertain remote-acceptance boundary may be retried as documented. |
| Release component inventory leaks local state | Disclosure through release metadata | The CycloneDX SBOM and third-party notices contain fixed component/version/distribution metadata only; installer validation rejects user paths, setup scratch, tenant/client identifiers, and token-shaped fields. | License/legal interpretation remains an external review responsibility. |
| TLS interception / DNS manipulation | Token or message exposure, delivery diversion | Required STARTTLS, normal hostname/certificate validation, DNS name rather than fixed IP, actionable failure diagnostics | A compromised trusted root or host resolver can subvert validation. |
| OAuth token sent to a hostile SMTP endpoint | Mailbox impersonation and token exfiltration | Production endpoint and token audience are fixed Exchange Online constants; only an internal test seam can replace the endpoint | Host/process compromise can alter running code and remains outside this control. |
| TLS downgrade or pre-TLS credential disclosure | Token or message disclosure | Require advertised STARTTLS, validated handshake, discard pre-TLS capabilities, require post-TLS XOAUTH2, and acquire/send the token only afterward | A compromised trusted root can still terminate TLS. |
| Credential or protocol-log leakage | Bearer-token reuse until expiry | No low-level credential logging; AUTH is represented only as redacted, credential bytes are zeroed, and token/Base64 log tests run at all levels | Managed strings held by MSAL and the token wrapper remain readable to a compromised process/debugger. |
| Malicious or stalling SMTP server | Memory/worker exhaustion or misleading diagnostics | Bound response line/count/total bytes, sanitize stored response text, retain short connect/TLS/command bounds, use a size-aware DATA streaming timeout, and independently bound the post-terminator final-response wait to 10 minutes | Slow operations can occupy a bounded worker until timeout. |
| Ambiguous remote acceptance | Duplicate mail after retry | Require final `250`; treat failures proven before terminator transmission as ordinary transient failures and classify uncertainty after terminator transmission begins as ambiguous; document at-least-once semantics | Exchange may have accepted a message whose final response RelayBridge did not receive. |
| Partial recipient acceptance | Duplicate delivery to already accepted recipients | V1 sends no DATA unless every recipient is accepted; RSET/close on any rejection | A server could violate SMTP transaction semantics; recipient-level partial delivery is unsupported. |
| SMTP response spoofing or injection | Incorrect queue state or unsafe logs | TLS authenticates the endpoint; parser requires same-code RFC multiline framing and bounds/sanitizes response text | A genuinely compromised Exchange endpoint or trusted TLS path can return deceptive but bounded responses. |
| Exchange RBAC misconfiguration or broad Entra permission | Unauthorized sender/mailbox use | XOAUTH2 user and MAIL FROM are the envelope sender; recommend resource-scoped `Application SMTP.SendAsApp`; prohibit additive broad Entra claim; require allowed and denied real-tenant tests | The dedicated-tenant negative mailbox failed closed and the tested Entra application had zero API permission entries; later tenant changes can still broaden scope. |
| Microsoft administrator credential/token capture | Tenant administrative compromise | The interactive helper invokes Microsoft's WAM flow in two short-lived private PowerShell processes. Entra remains hidden; Exchange receives a temporary worker-owned console parent while all script/result streams remain redirected. Passwords/factors are entered only into Microsoft UI; access tokens, auth codes, cookies, and cache serialization have no IPC field and never enter Host. Explicit disconnect and process exit end RelayBridge-owned privilege. | Windows/browser/WAM may retain normal OS-owned SSO state. A compromised interactive helper/process can observe its own short-lived administration session. The temporary Exchange console is visible with a neutral title so WAM modality is not weakened. |
| PowerShell injection through setup values | Arbitrary commands with administrator authority | Executors contain fixed allowlisted script source. GUID/sender/public-certificate values travel as bounded Base64 JSON data, not source; strict result DTOs reject unknown/duplicate/token fields. No arbitrary cmdlet or script crosses IPC. | A defect in the fixed Microsoft administration script could still perform unintended operations and requires adversarial review. |
| Launcher/bootstrap hijack, worker replacement, fake pipe server, or replay | Unauthorized local provisioning attempt or administrator code execution | Parameter-free URI grants no authority. Before launch and again on connection, Host validates the sidecar-free NativeAOT launcher plus a pinned exact release manifest for every file in the dedicated launcher/worker execution closure. The first-instance pipe rejects remote clients. Service obtains the native launcher's kernel-reported PID, requires its process-token SID to equal the impersonated pipe SID, and then checks interactive session, exact installed path and launcher hash before creating a random connection-bound session. Before accepting input, the launcher requires the pipe server's kernel-reported PID to equal the running SCM-owned `RelayBridge` service PID; SCM must report an own-process `LocalSystem` service with the exact installer-protected sibling `Host\RelayBridge.Host.exe` binary path. This avoids cross-integrity process/token access. Before confirmation, the worker independently binds itself to the kernel-reported parent PID and the exact protected launcher path/hash/session/SID from the Host-authenticated frame. Strict ordered messages and native action/sender confirmation prevent silent use. | Management is still unauthenticated loopback; another local user can launch the approved launcher and cause a confirmation prompt, but direct/copy-launched workers cannot display the RelayBridge confirmation or start cloud work. The launcher still cannot bypass Microsoft administrator authentication. A launch-intent nonce remains optional low-risk prompt-spam hardening; multi-user native setup is not claimed. An Administrator/SYSTEM attacker remains outside this local execution-trust boundary. |
| Named-pipe spoofing, stalling, or malformed IPC | Local privilege confusion or service denial | Explicit local ACL including Network deny, remote-client rejection, actual client-process/SID verification, one first instance, 4 KiB length prefix, strict JSON, duplicate/unknown rejection, version/session checks, ordered fixed enums, one short pre-authentication deadline, and sanitized results | Repeated local connection attempts can consume bounded setup-listener work; pipe creation/accept/processing failures are contained and retried without stopping SMTP, queue, or the Host. |
| Private launcher/worker/PowerShell/module/PATH hijack | Administrator code execution | Absolute approved paths, `-NoProfile`, controlled module environment, exact private Graph 2.25.0 and Entra 1.3.0 manifests loaded in dependency order, canonical module-base/version and command-source checks, disabled autoload, in-process `PSModulePath` lockdown, SYSTEM/Administrators/TrustedInstaller ownership by SID, ACLs without ordinary-user explicit mutation, raw `GENERIC_WRITE`/`GENERIC_ALL`, DACL, or delete-child rights, non-reparse traversal, pinned setup/tooling manifest hashes, per-file SHA-256, deterministic complete trees, applicable publisher checks, prelaunch/connection launcher validation, between-stage tooling revalidation, and no fallback. M8 packages the fixed Program Files hierarchy and exact private closures with MSI-authored protected ProgramData ACLs. Disposable Windows 11 acceptance verified effective Program Files ownership/ACLs, ordinary-user tamper denial, protected `SetupScratch`, non-reparse traversal, frozen verifier acceptance, exact helper/tooling closure, the custom-URI/service boundary, and servicing behavior. | A managed self-contained single-file boundary is intentionally not used. An administrator-level attacker can replace broader application or SCM configuration. There remains an unavoidable interval between the final integrity read and OS image load, mitigated by the non-writable tree. Windows Server, RDP, and Server Core installation behavior is not claimed. |
| User-controlled CLR startup hook, profiler, diagnostic, dependency, or runtime-root environment | Code execution before trusted managed setup code | The Host authenticates a sidecar-free NativeAOT launcher, so CLR startup variables cannot execute code before the first trusted launcher instruction. It constructs the worker and PowerShell environments from an explicit allowlist, omits .NET/CoreCLR/COR/COMPlus injection and runtime-redirection categories, sets `DOTNET_EnableDiagnostics=0`, and publishes the worker apphost with global-only runtime search. Startup-hook positive-control and hostile-environment process tests cover the launcher, worker, and child policy. | Exact production-environment WAM validation remains required. A compromised Administrator, SYSTEM, TrustedInstaller, kernel, or Microsoft authentication broker is outside this boundary. |
| Attacker-selected temporary or proxy environment | Generated EXO module execution or privileged traffic routing through attacker-controlled locations | Host creates a fresh lock-tracked session beneath installer-protected ProgramData after authenticating the launcher. Root/session ownership, DACL, delete-child and reparse checks fail closed. Launcher, worker and both PowerShell children replace `TEMP`/`TMP` with that path; ExchangeOnlineManagement 3.9.2 receives it through `-EXOModuleBasePath`. Raw proxy variables are omitted, and user profile folders are rebuilt through Windows known-folder APIs. | The exact interactive SID must write the session directory for EXO; ACLs do not isolate RelayBridge from an already-compromised concurrent process running as that same administrator. Windows/WAM may independently honor protected OS networking policy. Real WAM/EXO validation of generated-module placement remains required. |
| Provisioning child survives cancellation/crash | Residual admin privilege | The native launcher owns a kill-on-close Job Object containing the worker and its sequential private Entra/Exchange children; Host disconnect or launcher cancellation terminates the RelayBridge-owned tree, waits for Exchange child exit/output drain before releasing its console lease, and no token returns to Host | WAM/browser processes are OS-owned and intentionally not killed. Crash dumps created independently by the OS remain an endpoint-security concern. |
| Generated script grants broad permissions | Unauthorized mailbox access | Entra serializes only public certificate material and uses a narrow authoritative raw Graph v1.0 read to require `AzureADMyOrg`, exactly one matching public-certificate credential, no client secret, zero API permission entries, and zero service-principal app-role assignments. Wrapper projections are not trusted for this decision. Exchange requires only the selected sender in the marked group, the exact group-backed scope filter, and exactly one expected scoped `Application SMTP.SendAsApp` assignment; positive authorization is checked. | A tenant administrator can later add broader permissions outside RelayBridge. The native-path out-of-scope control-mailbox test remains a freeze gate. |
| Existing Exchange object collision or repeated setup | Scope takeover or duplicate grants | Scripts validate application ownership markers, service-principal identity, the exact group membership set, exact management-scope filter, and complete SMTP role-assignment set before reuse; additive or conflicting state stops without overwrite; reruns for the same installation are idempotent | Manual tenant changes can require administrator repair. |
| Stale Entra-stage resume | Old tenant/application identity authorizes a changed setup candidate | Resume reconstructs a reusable Entra result only from the authoritative active candidate when its activation identity, mode, certificate reference, tenant/client/service-principal identifiers, sender, completed stage, and fingerprint inputs are all complete and current. Replacement or incomplete state follows the full Entra path. Only the Entra stage is skipped; Exchange still authenticates and validates normally. No administrator token or WAM credential is persisted or reused. | A tenant administrator can change remote objects after local persistence; the continuing Exchange stage and final identity/SMTP validation remain required before activation. |
| Candidate setup damages a working connection | Delivery outage | Persist candidate progress separately; every native result is bound to immutable activation/revision/fingerprint context and applied by compare-and-swap. Validate local certificate, Exchange token, and actual SMTP sender path before one transaction rechecks the candidate and commits active identity/sender/activation. Cancel/replacement before commit leaves active state unchanged. | Microsoft resources created during a cancelled attempt require explicit administrator cleanup. Cancellation arriving after the atomic commit cannot undo a completed activation. |
| Pasted setup result executes content or exhausts memory | Local code execution or denial of service | Treat input as strict JSON data only; 4 KiB UTF-8 limit, unknown/duplicate-property rejection, exact typed fields, and no evaluation or PowerShell execution | Identifiers are still administrator-supplied and can be incorrect, causing validation failure. |
| Private-key export through setup UI | Microsoft application impersonation | Reuse the M3 public-only `.cer` exporter; no PFX path or exportable-key workflow; tests re-import output and require `HasPrivateKey=false` | A local administrator/process with key-store access remains privileged. |
| Premature “Microsoft 365 Ready” state | False security/readiness claim | Distinct certificate, identity, SMTP, sender, and test states; after restart persisted identifiers are Verification required; token acquisition uses the explicitly captured identity configuration; completed identity/Exchange evidence is attempt-scoped, ordered by a shared monotonic sequence, and filtered to the matching active fingerprint; incomplete Exchange attempts do not replace completed evidence; creation revalidates and transactionally checks the reviewed configuration | SMTP `250` proves Microsoft acceptance, not inbox receipt; later tenant-policy changes are discovered by the next explicit/normal operation rather than polling. |
| Crash or power loss | Lost or duplicated mail | Durable file flush, same-volume atomic promotion, SQLite FULL commit before SMTP 250, atomic claims, persisted retry state, and bounded idempotent startup reconciliation are implemented and failure-injection/restart tested. Orphan deletion requires a successful queue snapshot and fresh database ownership query. | Confirmed pre-commit orphans are deleted because SMTP did not accept them; database uncertainty preserves files. Ambiguity after remote or local acceptance can still produce duplicates. Physical power-loss behavior depends on storage hardware honoring flush. |
| Missing/corrupt local payload | Endless retries or silent loss | Startup and pre-delivery checks mark missing accepted payloads as diagnosable permanent storage failures and log them prominently | RelayBridge cannot reconstruct content already lost below its durability boundary. |
| Queue worker outage or hang | Delivery backlog and shutdown delay | Bounded worker count, one cancellation-aware activation latch, work signal plus safety poll, cheap health state, bounded graceful stop, forced cancellation, and stale-claim recovery. The latch opens only after authoritative Microsoft activation and does not create a second worker. | A provider that ignores cancellation can outlive the shutdown wait until the process terminates. |

## Security invariants

- Do not return SMTP success after DATA until durable local queue acceptance.
- Do not silently delete or discard queued mail.
- Do not disable outbound TLS validation.
- Do not store or log plaintext passwords, OAuth tokens, or private keys.
- Do not combine an RBAC-scoped SMTP grant with an unscoped Entra grant.
- Do not report “Microsoft connected” until real scoped SMTP OAuth delivery succeeds.
- Do not receive Microsoft administrator passwords/tokens in the service or retain
  administrator privilege. Only the authenticated NativeAOT launcher owns Host setup
  authority; fixed administrative PowerShell may run only beneath its clean-environment
  worker process tree and never as a generic shell.
- Do not activate candidate Microsoft settings until certificate, token, and actual
  scoped SMTP sender validation succeed; preserve a prior working configuration.
- Do not expose the management UI beyond loopback without authentication and
  CSRF/session protections. The host owns a loopback listener and rejects effective
  non-loopback URL/Kestrel overrides at startup.
- Do not advertise STARTTLS until a valid certificate and protected private key are
  configured. Until then, keep the listener loopback-only and cleartext AUTH
  disabled by default; enabling either LAN binding or cleartext AUTH is an
  explicit compatibility risk.

## Milestone gates

Milestone 4 automated parser, TLS, token-use, redaction, envelope, streaming,
size, cancellation, final-acceptance, queue, and large-message tests pass.
Allowed-sender success and out-of-scope sender failure were proven against a
dedicated real tenant. A fixture-matched actual RelayBridge 25 MiB multipart/base64
scan reached final `250`, persisted Delivered, and cleaned up its spool; Milestone 4
is frozen. Exchange size remains content/conversion dependent, and upstream
`554 5.2.270` remains a permanent `MessageTooLarge` result.
